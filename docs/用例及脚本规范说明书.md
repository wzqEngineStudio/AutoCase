## 1. 用例文件规范

### 1.1 文件命名规则

#### 1.1.1 文件名格式

用例文件必须以 `Case.json` 或 `case.json` 结尾，格式如下：

```
{用例编号}Case.json
{用例名称}Case.json
{用例编号}_{用例名称}Case.json
```

#### 1.1.2 命名示例

| 规范命名 | 说明 |
|----------|------|
| `TC001Case.json` | 仅用例编号 |
| `LoginCase.json` | 仅用例名称 |
| `TC001_LoginCase.json` | 编号+名称 |
| `TC002_UserRegisterCase.json` | 编号+多词名称 |

#### 1.1.3 命名约束

- ✅ 文件名中可以包含字母、数字、下划线
- ✅ 大小写不敏感（`Case.json` 和 `case.json` 均可）
- ❌ 不允许使用空格或特殊字符
- ❌ 不允许以数字开头

### 1.2 JSON 结构规范

#### 1.2.1 完整结构

```json
{
  "casesID": "TC001",
  "group": "用户模块",
  "version": "1.0",
  "severity": "High",
  "priority": "P0",
  "caseInfo": {
    "caseName": "登录成功",
    "description": "验证用户使用正确账号密码登录系统",
    "precondition": "用户已注册且账号处于正常状态",
    "stepsToReproduce": [
      "打开登录页面",
      "输入用户名: admin",
      "输入密码: 123456",
      "点击登录按钮"
    ],
    "remark": "备注信息"
  },
  "expectedResult": {
    "description": "用户成功登录系统",
    "checkpoints": [
      "页面跳转到首页",
      "显示用户昵称",
      "菜单显示正常"
    ]
  },
  "execution": {
    "timeout": 60000,
    "retryCount": 0
  },
  "environment": {
    "os": "Windows 10",
    "browser": "Chrome 100"
  },
  "metadata": {
    "createdBy": "张三",
    "createdTime": "2026-07-01T10:00:00",
    "updatedTime": "2026-07-15T14:30:00"
  },
  "currentStatus": "UNVERIFIED",
  "associatedCases": ["TC002", "TC003"],
  "mutuallyExclusiveCases": ["TC004"],
  "customField1": "自定义值",
  "customField2": {"nested": "value"}
}
```

#### 1.2.2 字段说明

##### 基础元数据（必填）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `casesID` | String | 是 | 用例唯一编号，如 TC001 |
| `group` | String | 是 | 用例所属分组/模块，如"用户模块" |
| `version` | String | 是 | 用例适用的版本号，如"1.0" |
| `severity` | String | 是 | 严重程度，见下表 |
| `priority` | String | 是 | 优先级，见下表 |

##### 严重程度枚举

| 值 | 含义 |
|----|------|
| Critical | 致命，阻塞发布 |
| High | 高，核心功能失效 |
| Medium | 中，次要功能失效 |
| Low | 低，建议改进 |

##### 优先级枚举

| 值 | 含义 |
|----|------|
| P0 | 最高优先级，必须立即执行 |
| P1 | 高优先级，本轮必须执行 |
| P2 | 中优先级，按需执行 |
| P3 | 低优先级，可选执行 |

##### 用例信息（必填）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `caseInfo.caseName` | String | 是 | 用例名称，简短描述 |
| `caseInfo.description` | String | 否 | 用例详细描述 |
| `caseInfo.precondition` | String | 是 | 执行前的前置条件 |
| `caseInfo.stepsToReproduce` | Array | 是 | 测试步骤列表 |
| `caseInfo.remark` | String | 否 | 备注信息 |

##### 预期结果（必填）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `expectedResult.description` | String | 是 | 预期结果描述 |
| `expectedResult.checkpoints` | Array | 否 | 检查点列表 |

##### 执行控制（可选）

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `execution.priority` | String | - | 执行优先级 |
| `execution.timeout` | Number | 60000 | 执行超时时间（毫秒） |
| `execution.retryCount` | Number | 0 | 失败重试次数 |
| `execution.tags` | Array | - | 标签列表 |
| `execution.dependsOn` | Array | - | 依赖用例ID列表 |

##### 环境约束（可选）

| 字段 | 类型 | 说明 |
|------|------|------|
| `environment.*` | Object | 测试环境约束，自定义键值对 |

##### 变更审计（可选）

| 字段 | 类型 | 说明 |
|------|------|------|
| `metadata.createdBy` | String | 创建人 |
| `metadata.createdTime` | String | 创建时间（ISO 8601） |
| `metadata.updatedTime` | String | 更新时间（ISO 8601） |

##### 关联关系（可选）

| 字段 | 类型 | 说明 |
|------|------|------|
| `associatedCases` | Array | 关联用例ID列表，执行时自动衔接 |
| `mutuallyExclusiveCases` | Array | 互斥用例ID列表，无法同时执行 |

##### 当前状态（系统维护）

| 字段 | 类型 | 说明 |
|------|------|------|
| `currentStatus` | String | 当前状态，由系统自动更新 |


## 2. 测试脚本规范

### 2.1 文件命名规则

#### 2.1.1 命名格式

测试脚本文件命名应与用例名称对应，格式如下：

```
{用例名称}Test.{扩展名}
{用例名称}.{扩展名}
{用例名称}_test.{扩展名}
```

#### 2.1.2 关联规则

系统通过名称模糊匹配自动关联脚本和用例，匹配规则：

1. 去掉脚本文件名的扩展名
2. 去掉末尾的 `Test`、`_test`、`Case`、`_case`、`Cases`、`_cases` 后缀
3. 与用例的 `caseInfo.caseName` 进行比较（忽略大小写和下划线）

#### 2.1.3 关联示例

| 用例名称 | 脚本文件名（匹配） | 脚本文件名（不匹配） |
|----------|---------------------|----------------------|
| 登录成功 | LoginTest.py | login_success.py |
| 登录成功 | Login.py | test_login.py |
| 用户注册 | UserRegisterTest.java | register.py |
| 数据导出 | DataExport_case.go | export.go |

### 2.2 脚本输出规范

#### 2.2.1 结果标记

脚本执行结果通过输出中的关键词或退出码判定，必须包含以下标记之一：

| 标记 | 含义 | 系统判定 |
|------|------|----------|
| PASS | 通过 | 执行成功 |
| FAIL | 失败 | 执行失败 |
| BLOCK | 阻塞 | 环境问题或前置条件不满足 |

#### 2.2.2 输出格式

脚本应在标准输出（stdout）中输出结果标记，格式示例：

```python
# Python示例
def test_login():
    try:
        # 测试逻辑
        if result == expected:
            print("PASS: 登录成功")
        else:
            print("FAIL: 登录失败")
    except Exception as e:
        print(f"BLOCK: {e}")
```

#### 2.2.3 退出码

除了输出标记外，脚本还可以通过退出码传递结果：

| 退出码 | 含义 |
|--------|------|
| 0 | 成功 |
| 非0 | 失败 |

#### 2.3.2 GDScript 模板

> **注意**：GDScript 官方不支持 `try...except` 语法，需要使用条件判断和断言进行错误处理。
> 
> **重要**：GDScript 脚本必须通过场景（`.tscn`）运行。系统在生成 GDScript 脚本时会自动生成对应的 `.tscn` 场景文件。

**GDScript 脚本模板**：

```gdscript
# @tool
# @icon("res://icons/test.png")
## 测试脚本: 登录成功
## 用例编号: TC001
## 优先级: P0
## 超时: 30秒 | 重试: 1次

extends Node

# ========== 用例元数据 ==========
var case_id: String = "TC001"
var case_name: String = "登录成功"
var priority: String = "P0"
var timeout_sec: int = 30
var retry_count: int = 1

# ========== 前置条件 ==========
## 用户已注册
func _setup_precondition() -> void:
	# TODO: 实现前置条件
	pass

# ========== 测试步骤 ==========
## 步骤1: 打开登录页面
func _step_1() -> void:
	# TODO: 实现步骤1
	pass

## 步骤2: 输入账号密码
func _step_2() -> void:
	# TODO: 实现步骤2
	pass

# ========== 预期结果 ==========
var expected_result: String = """
用户成功登录系统并跳转到首页
"""

# ========== 测试执行 ==========
func _ready() -> void:
	var start_time_msec := Time.get_ticks_msec()
	var success: bool = true
	var error_msg: String = ""

	# GDScript不支持try-catch，使用条件判断和断言进行错误处理
	if is_instance_valid(self):
		_setup_precondition()
	else:
		success = false
		error_msg = "节点无效"

	if success and is_instance_valid(self):
		_step_1()
	else:
		if success:
			success = false
			error_msg = "步骤1执行失败"

	if success and is_instance_valid(self):
		_step_2()
	else:
		if success:
			success = false
			error_msg = "步骤2执行失败"

	var elapsed := Time.get_ticks_msec() - start_time_msec
	if success:
		print("PASS: 测试通过")
		print("[执行耗时] %dms" % elapsed)
		get_tree().quit(0)
	else:
		print("FAIL: 测试失败 - %s" % error_msg)
		print("[执行耗时] %dms" % elapsed)
		get_tree().quit(1)
```

**自动生成的 `.tscn` 场景文件**：

```tscn
[gd_scene load_steps=2 format=3]

[ext_resource type="Script" path="res://LoginTest.gd" id="1"]

[node name="LoginTest" type="Node"]
script = ExtResource("1")
```

**场景文件说明**：
- 使用 Godot 4.x 格式（`format=3`）
- 根节点类型为 `Node`，与脚本中的 `extends Node` 对应
- 通过 `ExtResource` 引用同目录下的 `.gd` 脚本文件
- 场景名称默认与脚本文件名相同（去掉扩展名）

**执行方式**：
```bash
godot --headless --scene LoginTest.tscn
```

## 3. 用例与脚本关联规范

### 3.1 关联机制

系统通过以下步骤自动关联用例和脚本：

1. 扫描目录下所有 `*Case.json` 文件，提取用例名称（`caseInfo.caseName`）
2. 扫描目录下所有脚本文件，提取脚本名称（去掉扩展名和末尾的 `Test`/`Case` 后缀）
3. 标准化名称：
   - 转换为小写
   - 去掉下划线和空格
4. 匹配相同名称的用例和脚本

### 3.2 命名一致性要求

为确保正确关联，用例名称和脚本文件名应满足：

**标准化规则**（按顺序执行）：
1. 去掉文件扩展名
2. 转换为小写
3. 去掉末尾的 `case`、`cases`、`test`、`_case`、`_cases`、`_test` 后缀
4. 去掉下划线和空格

| 用例名称 | 脚本文件名 | 脚本标准化后 | 用例标准化后 | 是否匹配 |
|----------|------------|--------------|--------------|----------|
| Login | LoginTest.py | login | login | 是 |
| LoginSuccess | LoginSuccess_test.py | loginsuccess | loginsuccess | 是 |
| UserRegister | UserRegisterCase.java | userregister | userregister | 是 |
| DataExport | DataExport_case.go | dataexport | dataexport | 是 |
| LoginSuccess | TestLogin.py | testlogin | loginsuccess | 否（前缀不匹配） |
| 用户登录 | 用户登录Test.py | 用户登录 | 用户登录 | 是（中文名称需完全一致） |

### 3.3 最佳实践

1. **保持名称一致**：用例名称和脚本文件名使用相同的英文名称
2. **使用统一命名风格**：推荐使用 PascalCase 或 snake_case
3. **避免中文名称**：脚本文件名尽量使用英文，便于跨平台兼容
4. **编号与名称结合**：文件名中包含用例编号，便于识别

## 4. 用例编写规范

### 4.1 编写原则

1. **原子性**：每个用例只验证一个功能点
2. **独立性**：用例之间相互独立，无执行顺序依赖
3. **可重复性**：用例可以重复执行，结果一致
4. **可验证性**：预期结果清晰明确，便于自动化判定

### 4.2 步骤编写规范

1. 步骤应简洁明了，每步只做一件事
2. 使用主动语态，如"输入用户名"而非"用户名被输入"
3. 步骤顺序合理，符合用户操作流程
4. 包含必要的测试数据

### 4.3 预期结果编写规范

1. 预期结果应具体、可量化
2. 包含多个检查点时，使用数组形式列出
3. 避免模糊表述，如"正常显示"应改为"显示用户昵称'张三'"

### 4.4 示例：良好的用例

```json
{
  "casesID": "TC001",
  "group": "用户模块",
  "version": "1.0",
  "severity": "High",
  "priority": "P0",
  "caseInfo": {
    "caseName": "登录成功",
    "description": "验证用户使用正确账号密码成功登录系统",
    "precondition": "1. 用户已注册账号 admin/123456\n2. 系统处于正常运行状态",
    "stepsToReproduce": [
      "打开浏览器，访问登录页面 http://localhost:8080/login",
      "在用户名输入框输入: admin",
      "在密码输入框输入: 123456",
      "点击「登录」按钮"
    ]
  },
  "expectedResult": {
    "description": "用户成功登录系统并跳转到首页",
    "checkpoints": [
      "页面URL变为 http://localhost:8080/home",
      "页面顶部显示用户昵称'admin'",
      "左侧菜单显示「首页」「用户管理」「设置」",
      "登录按钮不再显示"
    ]
  }
}
```

### 4.5 示例：需要改进的用例

```json
{
  "casesID": "TC002",
  "group": "用户模块",
  "version": "1.0",
  "severity": "High",
  "priority": "P0",
  "caseInfo": {
    "caseName": "登录失败",
    "description": "测试登录失败情况",

      "登录",
```

**改进建议**：
- 步骤不完整，缺少打开页面、输入用户名等步骤
- 预期结果模糊，应明确错误提示内容和页面状态
- 缺少具体的测试数据

## 5. 版本控制规范

### 5.1 用例文件版本管理

用例文件应纳入版本控制系统（如 Git），建议：

1. 每个用例文件独立管理
2. 使用语义化版本号（如 1.0.0）

| 分支 | 用途 |
